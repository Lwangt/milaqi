# 米拉奇战纪 · 技术方案选型决策文档

> 版本 v1.0 ｜ 状态：待你决策
> 本文档只做【技术选型】，不含完整策划案。
> 事实核对时间点：Godot 4.6.1 stable / Unity 6.3 LTS (6000.3.x) / Unreal Engine 5.8

---

## 0. 先看结论（TL;DR）

| 项 | 结论 |
|---|---|
| 首选 | **Godot 4.6 + C#(.NET)**：UDP/ENet 原生直连 IP，Windows 导出可执行文件 |
| 次选 | **Unity 6.3 LTS + URP + NGO/UTP**：生态与资源商店最强，性能与画质天花板更高 |
| 慎选 | **Unreal 5.8**：画质天花板最高，但安装/编译/资产门槛会让开发周期翻 3~5 倍 |
| 不推荐 | 纯自研 .NET（MonoGame/Stride）、Web(Three.js)+Tauri，理由见第 3 章 |

**最关键的三个问题（比选引擎更重要）：**

1. **美术维度**：2D 骨骼立绘 / 2.5D / 全 3D 俯视 —— 决定 80% 的美术工作量。
2. **同步模型**：主机权威（推荐）还是确定性帧同步 —— 决定联机开发难度差 5 倍。
3. **IP 直连的真实边界**：局域网稳、公网要端口映射、默认没有 NAT 穿透，详见 5.2。

## 1. 需求 → 技术硬指标推导

从玩法描述（回合经济 + 实时自动战斗 + 30 兵种 + 遗物/商店/技能 + 双人联机）反推：

| 玩法事实 | 推导出的技术硬指标 |
|---|---|
| 兵种自动前进、索敌、战斗 | 单位级 AI + 寻路；每方同屏 50~300 单位，峰值 800+ |
| 战场上兵更多就按杀戮值对敌方城邦造成伤害 | 每回合需对同一份战场快照做**一致结算**（双方看到的战场必须一样） |
| 回合经济/人口成长、云顶式等级体系 | 数据驱动配置表，改平衡不重新编译 |
| 30+ 兵种，8 项属性各不相同 | 配置驱动 + 公式化结算，禁止把数值写死在代码里 |
| 遗物 / 宝石商店 / 技能强化 | 需要效果系统（Effect/Modifier + 钩子），遗物 = 数据 + 若干可组合效果 |
| 技能可对特定区域释放（王国保卫战式） | 区域选取 + 射线拾取 + 技能释放同步 |
| 双人对战、填对方 IP 互联 | P2P（主机-客户端）UDP，固定端口，双击即用 |
| 相对高画质的可执行文件 | GPU 渲染管线（Vulkan/DX12）、骨骼动画、粒子、光照；包体 0.5~5GB |
| 遗物随回合出现、双方各自选择 | 回合状态机 + 同步随机种子，双方抽到的遗物必须一致 |

**规模量级总结（决定一切）：**

- 逻辑对象：约 1000 单位 × 8 属性 + 状态机，每秒 20~30 次模拟 tick
- 表现对象：同屏 300~800 个几何/骨骼动画
- 网络：2 人；命令带宽 < 1KB/s，快照同步 20~100KB/s
- 反作弊要求：低（朋友间对战），不需要专用服务器

## 2. 五个先决技术问题（回答完再选引擎）

### Q1 美术维度（工作量差 5 倍）

| 方案 | 表现 | 工作量 | 适合 |
|---|---|---|---|
| A 纯 2D 骨骼动画（Spine/DragonBones 风格） | 高，类王国保卫战/明日方舟 | 中（需美术出骨骼动画） | 兵种多、产能有限 |
| B 2.5D：3D 地形场景 + 2D billboard 单位 | 中高，有纵深 | 中高 | 想看起来像 3D 但不想做 30 套模型 |
| C 全 3D 俯视（自走棋视角） | 高，可上 Lumen/全局光照 | 最高（30 兵种 × 模型+动画+特效） | 目标 3A 观感 |
| D 程序化占位 + 后续替换 | 低起步，可迭代 | 最低 | **原型阶段推荐**，先验证玩法 |

> 30+ 兵种 = 30 套美术资产，这是整个项目最贵的部分，比引擎选择贵 10 倍。任何技术方案都必须能在占位美术下跑通全流程。

### Q2 同步模型

| 关注点 | 主机权威 Host-Authoritative | 确定性帧同步 Lockstep |
|---|---|---|
| 原理 | 一方当主机跑全部模拟，定期把状态/事件发给对方 | 双方只交换指令，各自本地跑同一套确定性模拟 |
| 带宽 | 20~100 KB/s（随单位数增长） | < 1 KB/s（恒定） |
| 开发难度 | 低：一份逻辑代码 | 高：禁浮点误差、寻路/物理/RNG 必须完全确定性，desync 极难调试 |
| 断线重连/观战 | 容易（重发快照） | 很容易（重放指令） |
| 回放 | 需自己录 | 天然免费 |
| 外挂 | 客户端可信度低 | 双方都掌握全量状态 |
| 本项目适配 | **推荐**：2 人、直连、单位多但只需看得见 | 过度设计 |

**推荐**：主机权威 + 20Hz 快照 + 客户端插值。未来要做回放/观战，再补确定性模拟，或直接录快照。

### Q3 单位规模怎么实现

| 方案 | 说明 | 各引擎支持 |
|---|---|---|
| 普通对象（GameObject/Node） | 每单位一个对象 + 脚本 | 300 内轻松，800+ 开始掉帧 |
| 数据导向 ECS/DOTS | 结构体数组 + 批处理 | Unity DOTS 最成熟；Godot 无官方 ECS |
| 逻辑/表现分离 + 批量渲染 | 逻辑跑纯数组，渲染用 MultiMesh/实例化 | **万金油，推荐**，任何引擎都能做 |

### Q4 表现层：真实 3D 还是骨骼 2D

2D 骨骼动画在 Godot / Unity 都有官方或成熟插件；UE 对 2D 支持较弱（Paper2D 已停止演进），这是 UE 的隐性局限。

### Q5 分发方式

| 方式 | 优点 | 局限 |
|---|---|---|
| 裸 exe 互发 + IP 直连 | 零成本、零门槛 | 无自动更新、无好友系统、公网需端口映射 |
| Steam（Steamworks P2P + 好友邀请） | **免 NAT 穿透**、自动更新 | 100 美元上架费 + 审核、绑定平台 |
| 自建中继服务器 | 免 NAT 穿透、可控 | 需服务器与运维成本 |

> 需求「选对方 IP 互联」= 方案 1。技术上可行，但只在局域网、或至少一方有公网 IP 且已做端口映射时可用。这是需求的物理限制，不是引擎限制。建议 v1 做 IP 直连并预留 Steam/中继接口。

## 3. 候选技术方案与局限性（重点）

### 方案 A：Godot 4.6 + C# (.NET) ｜ 推荐

构成：Godot 4.6.1 stable (.NET 版) + C# + 内置 ENetMultiplayerPeer + 纯 C# 逻辑层 + MultiMesh 批量渲染 + Vulkan Forward+。

- **IP 直连**：CreateServer(port) / CreateClient(ip, port) 引擎原生支持，UDP，零第三方依赖。
- **画质上限**：Vulkan Forward+、SDFGI 全局光照、SSAO、体积雾、GPU 粒子、2D/3D 骨骼动画。风格化画质（卡通/像素/低多边形）能做得很好；写实 3A 不如 UE5。
- **单位规模**：GDScript 慢，但 C# + 逻辑表现分离 + MultiMesh 可稳跑 500~1000 个简单 2D 单位；Godot 4.6 物理可切 Jolt，更稳更快。
- **开发效率**：极高。场景与资源是纯文本（.tscn/.tres），可 diff、可脚本生成、可 headless 跑测试、可命令行一键导出 exe。
- **包体**：空项目 exe 约 60~90MB，可按模板裁剪，资源另计。
- **许可**：MIT，完全免费，无版税，无收入门槛。
- **局限性**：
  1. 主机游戏（PS/Xbox/Switch）无官方导出，需第三方（W4 Games）商业授权；只做 PC 无影响。
  2. 无官方 ECS，大单位数需自己写数据导向逻辑。
  3. 资源商店与第三方插件生态远小于 Unity。
  4. 写实 3D 画质与影视级动画工具链弱于 UE5。
  5. C# 版导出需 .NET SDK（本机只有 6.0.12 运行时，需补装 .NET 8/10 SDK）。
  6. 中文社区与商业案例少于 Unity。

### 方案 B：Unity 6.3 LTS + URP/HDRP + NGO(UTP)

构成：Unity 6.3 LTS (6000.3.x) + URP 或 HDRP + Netcode for GameObjects（Unity Transport，UDP 直连 IP）+ 可选 DOTS/ECS + Addressables。

- **IP 直连**：UnityTransport.SetConnectionData(ip, port) + StartClient()，原生支持；也可换 Mirror / FishNet（FishNet 带宽与 CPU 更优）。
- **画质上限**：URP 中高 / HDRP 高。Shader Graph、VFX Graph、Timeline、Cinemachine 工具链成熟，最容易做出「看起来很贵」。
- **单位规模**：DOTS/ECS + Burst + Jobs 业界最强（上万单位），但与常规 GameObject 是两套世界观，学习曲线陡。
- **开发效率**：编辑器强，但场景/预制体是 YAML + GUID 引用，脚本化生成与 diff 困难，重度依赖打开编辑器。
- **包体**：空项目 60~120MB，含资源通常 1~5GB。
- **许可**：Unity Personal 免费（年收入/融资 < 20 万美元），Unity 6 起可关闭 Made with Unity 启动画面；Runtime Fee 已于 2024-09-12 正式取消。超过门槛需 Pro 订阅（每年每席位数千元人民币量级，以官网为准）。
- **局限性**：
  1. 编辑器许可 + 首次安装含模块约 20GB+；本机 C 盘仅剩 23GB，必须装到 D 盘。
  2. 手写/脚本化产出场景容易损坏（GUID/meta 引用链），自动化程度不如 Godot。
  3. 想跑上千单位必须上 DOTS，等于再学一套引擎。
  4. 2D 骨骼动画（Spine）为第三方付费资产。
  5. 版本升级偶有破坏性变更，锁 LTS 后不要随意升级。

### 方案 C：Unreal Engine 5.8 + C++

- **画质上限**：最高（Lumen、Nanite、Chaos、Niagara），最直接满足「相对高画质」。
- **IP 直连**：Listen Server 模式，客户端 open <ip>，Replication 成熟，属性同步与 RPC 开箱即用。
- **单位规模**：普通 Actor 数百单位可控，上千需 Mass Entity（又是一套框架）。
- **局限性（对本项目较致命）**：
  1. 安装约 100~150GB（引擎 + VS + 模块），C++ 全量构建 10~40 分钟，热重载常出问题。
  2. 蓝图是二进制资产，无法用文本/脚本批量生成；30+ 兵种、几十件遗物这类大量重复内容做起来极痛苦。
  3. C++ 门槛高、迭代慢，做 2D 风格化游戏属于高射炮打蚊子。
  4. 2D 工作流（Paper2D/PaperZD）生态远弱于 Unity/Godot。
  5. 许可：免费，但产品生命周期总收入超 100 万美元后收 5% 版税。
  6. 包体普遍 GB 级，启动慢。

### 方案 D：纯 .NET 自研（MonoGame / Stride / Silk.NET + LiteNetLib）

- **优点**：C# 全栈统一、编译秒级、可 100% 自动化开发与测试、无引擎黑盒、包体极小（<50MB）、IP 直连极简单。
- **缺点（决定性）**：画质天花板最低。渲染管线、骨骼动画、粒子、UI、场景编辑器、物理、寻路全要自己写，等于自己造半个引擎，工期不可控。Stride 比 MonoGame 强但社区极小。
- **适用**：只做像素/矢量 2D，且接受「程序员美术」。

### 方案 E：Web 技术（Three.js / Phaser / Cocos）+ Tauri 或 Electron

- **优点**：跨平台、UI 开发极快、可全自动开发、热重载爽。
- **缺点**：与「高画质可执行文件」需求直接冲突。WebGL/WebGPU 包体大（Electron 空壳 150MB+）、显存与驱动受限、无原生 Vulkan 管线；800 单位物理寻路在 JS 上吃力；**IP 直连做不到**（WebRTC 必须经过信令/STUN/TURN 服务器），与需求冲突。
- **结论**：不推荐。

### 方案 F：Bevy / Rust 自研
性能与包体优秀，但生态年轻、无成熟编辑器、开发速度慢，同样面临自己造引擎的问题。不建议。

## 5. 关键技术点横向对比

### 5.1 网络库对比

| 库 | 引擎 | IP 直连 | 说明 |
|---|---|---|---|
| ENetMultiplayerPeer（内置） | Godot | 原生支持 | 可靠/不可靠 UDP + RPC，零依赖，最省事 |
| Unity Transport + NGO | Unity | 支持 | 官方维护，文档全 |
| FishNet | Unity | 支持 | 性能与带宽优于 NGO，社区活跃，免费 |
| Mirror | Unity | 支持 | 老牌，教程多，架构偏传统 |
| Unreal Replication | UE | 支持 open ip | 开箱即用但概念多（网络相关性/优先级） |
| LiteNetLib | 任意 .NET | 支持 | 自研方案首选，轻量 |
| Steamworks P2P | 全平台 | 免 NAT | 需 Steam 上架，是解决公网互通的正解 |

### 5.2 「填对方 IP 就能联机」的真实边界（重要）

| 场景 | 能否直连 | 需要做什么 |
|---|---|---|
| 同一局域网 | 可以 | 开放 UDP 端口（Windows 防火墙放行） |
| 一方有公网 IP | 可以 | 主机方路由器做端口映射 Port Forwarding |
| 双方都在 NAT 后面（最常见的家庭宽带） | **不能** | 需 NAT 穿透 STUN + 中继 TURN，或 Steam P2P |
| 跨运营商/校园网/公司网 | 通常不能 | 同上，UDP 被封时甚至要走 TCP/TLS 中继 |

**结论**：需求技术上成立，但默认只在局域网或公网 IP 场景可用。若想和外地朋友随时开局，最终必然要加房间服务器 + 中继，或上 Steam。

**架构演进建议：**

1. v1：主机/客户端 UDP 直连（IP + 端口），局域网开黑 100% 可用。
2. v2：轻量房间服务器（只做撮合 + UDP 打洞），直连不成自动降级中继。
3. v3（可选）：接 Steamworks，好友邀请一键进房，彻底免网络配置。

### 5.3 同步模型再对比（影响最大）

| 关注点 | 主机权威 | 确定性帧同步 |
|---|---|---|
| 移植/改逻辑负担 | 无 | 极大（禁浮点、禁容器顺序依赖、逻辑表现严格分离） |
| Desync 风险 | 无 | 高且难复现 |
| 带宽 | 随单位数增长 | 恒定极低 |
| 回放/观战 | 需额外做 | 天然 |
| 迟到加入 | 简单 | 复杂 |
| 本项目适配 | 合适 | 过度设计 |

### 5.4 存档 / 回放 / 平衡调整

- **配置表驱动**：兵种/遗物/技能/经济曲线全部放 data 目录（CSV 或 JSON），启动加载，改数值不重编译。
- **回放**：主机权威下录制每 tick 快照 + 指令即可，一局几十 KB。
- **平衡工具**：写 headless 批处理模式，双方 AI 对战 ×1000 局统计各流派胜率；这是流派出场率/胜率调优的核心手段，方案 A/D/E 极易实现，UE 实现麻烦。

## 6. 推荐结论

**推荐方案 A：Godot 4.6 (.NET) + C#**，理由按权重：

1. IP 直连是原生能力，完全命中「填对方 IP 联机」需求，零第三方依赖。
2. 内容量爆炸（30 兵种 / 50+ 遗物 / 多流派）需要批量生成与数据驱动，Godot 纯文本场景 + C# 数据层最合适，避免每加一个兵种都要开编辑器点半天。
3. 磁盘与依赖最轻（引擎约 200MB）；本机 C 盘只剩 23GB，装 Unity/UE 必须挪到 D 盘且耗时数小时。
4. 可 headless 跑自动化测试与平衡批模拟，这是长线平衡迭代的关键。
5. MIT 免费无版税，未来上架无额外成本。
6. 2D/2.5D 风格化画质（Vulkan + 全局光照 + GPU 粒子 + 骨骼动画）已能达到「相对高画质」的观感。

若你更看重「别人一眼觉得画面很贵」且愿意承担更重的工具链，选 **方案 B（Unity 6.3 + URP）**；
只有确定要做写实 3D 大场面且不介意工期翻数倍，才选 **方案 C（UE5.8）**。

## 7. 坦白说：AI 开发代理的现实约束（会影响你的选择）

本项目将由我（AI 代理）承担大量实现工作，不同引擎的可自动化程度差异极大：

| 引擎 | 我能做什么 | 我做不了 / 很吃力 |
|---|---|---|
| **Godot** | 直接生成 .tscn/.tres/.cs 文本文件；headless 跑逻辑与单元测试；命令行一键导出 exe；形成「写代码 → 自动测试 → 看结果」闭环 | 需要人眼判断的美术表现，需截图人工确认 |
| **Unity** | 写 C# 脚本没问题；可跑 -batchmode -runTests | 场景/预制体 YAML+GUID 手改易坏；需要编辑器 + 账号许可激活；无编辑器时无法可靠产出可运行场景 |
| **UE5** | 写 C++ 子集 | 蓝图是二进制资产无法可靠生成；全量 C++ 编译 10~40 分钟；安装 100GB+；几乎无法自动化迭代 |
| **自研 .NET / Web** | 100% 自动化 | 但要自己造渲染管线/动画/UI，画质与工期不可控 |

> 直说：选 UE5，我基本只能当「写 C++ 的助手」，你需要花大量时间在编辑器里手工搭建；选 Godot，我可以端到端把游戏做出来并自测。这是我把 Godot 排第一的重要现实原因之一。
