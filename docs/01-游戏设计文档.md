# 米拉奇战纪 · 游戏设计文档 (GDD v3.2)

> 数值表由 `data/*.json` 自动生成。引擎 Godot 4.6.1 (.NET)，逻辑层纯 C#，可 headless 测试。

## 1. 概述

双人实时对抗 + 回合经营 + 自动战斗。双方城邦各 190 点生命。

```
战后对敌方城邦造成的伤害 = max(0, 我方存活单位杀戮值总和 − 敌方存活单位杀戮值总和)
回合结构：备战(40s) → 交战(最长 38s) → 结算(扣血后清空战场)
```

## 2. 部队规则

- 买下的兵**永久属于你**，战斗中阵亡不会失去它
- 购买后进入【待出战队列】：选中 → 点战场自己那半边放下；点已上场的可撤回
- 每回合开始按阵容**满血重新摆出**；结算完毕**清空战场**

## 3. 经济、等级与解锁

| 项 | 规则 |
|---|---|
| 基础收入 | 5 金 / 回合 |
| 利息 | 每 10 金产 1 金，上限 5 |
| 连胜连败 | 2 连 +1，3 连 +1，4 连 +2，5 连及以上 +3 |
| 等级 | 起始 3，最高 12；买经验 4 金 = 4 点 |
| 人口上限 | **= 等级 + 1** |
| **兵种解锁** | **按等级**：Lv1 / Lv3 / Lv5 / Lv7 / Lv9 / Lv11 |

升级所需经验：0 / 2 / 2 / 6 / 10 / 16 / 26 / 40 / 58 / 78 / 100 / 130

## 4. 战斗

```
物理伤害 = max(物攻 × (1 − 物防/(物防+75)), 物攻 × 0.2)
魔法伤害 = max(魔攻 × (1 − 魔防/(魔防+75)), 魔攻 × 0.2)
```

主循环：`ShuffleOrder`（每 tick 随机打乱处理顺序）→ 索敌 → 移动/攻击 → `Separate`（累加推力后统一应用）

### ⚠️ 已确认的收敛障碍

这个系统**不可用「调参」精调**，实测证据：

1. **强耦合**：一个流派涨 30%，会通过配对把其他六个各拉低约 5%，总胜率恒定为 50%
2. **阶跃响应**：把万箭齐发的标签权重从 1.2 降到 0.8（−33%），它的胜率从 71.3% 掉到 35.4%（−36 点）；
   同一轮里亡灵虫群只把 tierBias 从 7 调到 8，胜率就从 57.9% 涨到 72.5%（+15 点）
3. **诊断工具**：`dotnet run -- cross <兵种A> <数量> <兵种B> <数量>` 可以测同人口跨兵种对抗，
   这是发现「射程系数把远程兵压低了 75%」的关键工具

**结论**：继续用「调印记数值」的方式迭代收益极低。下一步应该改为**给每个流派固定一组经过验证的阵容模板**，
或者引入「流派内兵种数量上限」这类结构性约束，而不是继续调系数。

```powershell
dotnet run -- cross archer 6 militia 6   # 同人口跨兵种对抗
dotnet run -- diag A B              # 单局逐回合诊断
```

### 公平性修复清单

| 现象 | 根因 | 修复 |
|---|---|---|
| 所有对局完全相同 | 战斗随机数是写死的常量 | 用对局种子初始化 |
| 纯战斗偏差 18% | 单位处理顺序固定 | 每 tick 随机打乱 |
| 近战仍偏 9% | Separate 边遍历边改坐标 | 先累加推力再统一应用 |
| 部署位置左右不同 | 双方各自抽随机数 | 严格镜像的确定性阵型 |
| 整体偏差 12~27% | 共用随机数流 | 每回合交替结算顺序 |
| HUD 背景盖住战场 | 背景加在 CanvasLayer 上 | 移到 Layer -1 |

当前：纯战斗偏差 0.5%~6.0%，整体对局偏差 2.0%。
